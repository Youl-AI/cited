# Cited — 설계 문서

> 작성일 2026-07-28

## 제품 개요

브랜드가 AI 답변에 얼마나 인용되는지 추적하는 한국어 GEO(Generative Engine
Optimization) 모니터링 SaaS.

소비자는 이제 "30대 남자 러닝화 추천해줘"를 검색창이 아니라 AI에게 묻는다.
AI는 문장으로 답하므로 브랜드는 자기가 그 답변에 등장했는지 알 방법이 없다.
Cited는 대신 AI에게 계속 물어보고 결과를 기록해 그 사각지대를 없앤다.

**챗봇이 아니다.** 고객이 AI와 대화하는 서비스가 아니라, 우리가 고객 대신 AI에게
매주 물어보고 결과를 대시보드로 보여주는 자동 모니터링 도구다. 가장 가까운
비유는 구글 애널리틱스다. 로그인하면 대시보드가 있고, 데이터는 자동으로 쌓이고,
사용자는 보러 들어온다. 메일은 "새 데이터가 나왔다"는 알림일 뿐 본체가 아니다.

고객이 손을 쓰는 곳은 두 군데뿐이다.

- 온보딩에서 질문·별칭·경쟁사 편집 (최초 1회 약 10분, 이후 가끔)
- 대시보드 열람 (주 1회 5분)

## 경쟁 현황과 포지셔닝

국내에 이미 플레이어가 있다. "아무도 안 한다"가 아니라 **"비싸게 하는 곳은
많은데 싸게 하는 곳이 없다"**가 정확한 상황이다.

| 구분 | 사업자 | 가격 |
| --- | --- | --- |
| 국내 에이전시 | 지오랭크, 넥스트티 OPTIGEO, 비즈스프링, 리드젠랩 | 1회 진단 50~150만원 / 월 컨설팅 400만원~ |
| 국내 네이버 추적 | NNT Insights, OPTIGEO | 비공개 (문의) |
| 해외 셀프서브 | Otterly.AI $29, Peec AI $89, Frase $39, KIME €149 | 공개 |

```
        셀프서브·저가        에이전시·고가
한국어    ← 여기가 비어 있다   지오랭크, 넥스트티, 비즈스프링
+네이버                        NNT Insights, OPTIGEO
────────────────────────────────────────────────
영어      Otterly, Peec        Profound
```

포지셔닝은 "우리만 한다"가 아니라 **"월 400만원 컨설팅을 29만원에"**다.
랜딩 문구도 그 축으로 간다.

블루오션이 아니라는 사실은 나쁜 소식이 아니다. 시장이 존재한다는 증거다.

**주의할 것 두 가지.**

- 무료 진단은 차별점이 아니다. 지오랭크 GEO Scanner, RanketAI가 이미 한다.
  리드 생성 장치로는 유효하지만 "우리만 준다"고 말하면 안 된다.
- 네이버 추적도 유일하지 않다. OPTIGEO와 NNT Insights가 이미 한다.

우리가 가진 자리는 **셀프서브 + 공개 가격 + 한국어 + 네이버**의 조합이다.
국내는 전부 상담 후 견적이고, 해외 셀프서브는 네이버를 보지 않는다.

| 항목 | 결정 |
| --- | --- |
| 1차 목표 | 매출 증명 = 포트폴리오 (둘 다) |
| 범위 | 풀 SaaS — 인증 + 자동결제 + 대시보드. 단 무료 진단을 먼저 배포 |
| 타깃 | 국내 D2C·이커머스 브랜드, 그리고 **대행사** |
| 엔진 | ChatGPT · Gemini · 네이버 AI 브리핑 · Google AI Overviews |
| 측정 | 주 1회, 샘플 LLM 3회 · SERP 2회 |
| 요금제 | Starter 99,000원 / Business 290,000원~ |
| 대표 지표 | Cited Rate (언급된 응답 / 전체 응답) |

### 요금제

| | 무료 진단 | Starter | Business |
| --- | --- | --- | --- |
| 가격 | 0원 | **99,000원** | **290,000원 ~** |
| 브랜드 | 1개 | 1개 | **3개** |
| 추적 질문 | 3개 | 10개 | 30개 (+10개당 90,000원) |
| 엔진 | LLM 2종 | 4종 (네이버 포함) | 4종 |
| 경쟁사 | 3개 | 3개 | 10개 |
| 히스토리 | — | 3개월 | 무제한 |
| 내보내기 | — | — | CSV |
| 측정량 | 1회성 6회 | 월 약 430회 | 월 약 1,290회 |
| 원가 | 건당 80~125원 | 월 약 11,300원 | 월 약 34,000원 |
| 원가율 | — | 11% | 12% |

> **무료 진단 원가는 2026-07-29에 정정됐다(50~110원 → 80~125원).** 최초 계산이
> 웹검색 툴의 **호출당 요금**을 빠뜨렸다 — 아래 "비용 구조" 절 참고. 정정된 값은
> 무료 진단을 **저가 모델**로 돌리는 것을 전제한다. 유료 플랜 원가(11,300 / 34,000)는
> 역산해 보면 호출당 39원을 전제하고 있어 실제 단가와 맞는다 — 틀린 것은 무료 진단뿐이었다.

**"추적 질문"은 사용 횟수가 아니라 상시 감시 대상이다.** 한 번 등록하면 매주
자동으로 다시 물어본다. Starter의 질문 10개는 "월 10번"이 아니라 월 약 430회
측정이다. 화면에도 그렇게 표기한다.

> 추적 질문 10개 · 매주 자동 측정 (월 약 430회)

### 네이버는 Starter부터 포함한다

이것이 요금 구조의 핵심 결정이다.

네이버를 Business 전용으로 두면 Starter는 **해외 툴(Otterly $29)보다 2.5배
비싸면서 엔진은 적은 상품**이 된다. 더 나쁜 것은, 타깃이 국내 D2C인데 우리
유일한 차별점이 고객 대부분에게 닿지 않는다는 점이다.

Starter에 네이버를 넣으면 원가가 5,200원 → 11,300원으로 오르지만 원가율은 11%다.
그 대가로 Starter가 "해외 툴이 못 하는 걸 하는 상품"이 된다.

결과적으로 **Starter와 Business의 차이는 규모(브랜드·질의·경쟁사)뿐**이다.
축이 하나라 애드온 구조가 명확해진다.

### 질의 팩은 종량제가 아니라 정액 애드온이다

원가가 질의 수에 정비례하므로 사용량 과금은 발상 자체는 옳다. 그러나 진짜
종량제(사용량 집계 → 월말 정산 → 변동 금액 청구)는 1단계에 넣지 않는다.

- 정액 빌링키 하나로 끝나던 결제가 사용량 집계·정산·변동 청구·청구 실패
  처리·사용량 대시보드로 통째로 늘어난다
- 예측 불가능한 청구는 B2B에서 흔한 해지 사유다. 마케팅 팀은 예산을 미리 잡는다
- 질의 1개 추가 원가는 월 약 1,100원이다. 받아봐야 큰 돈이 아닌데 복잡도만 크다

대신 **정액 애드온**으로 같은 목적을 달성한다.

```
Business 기본        30질의    월 290,000원
  + 질의 팩 10개     +10질의   월  +90,000원
                     40질의    월 380,000원
```

고객에게는 "쓴 만큼 낸다"가 그대로 성립하면서 금액이 예측 가능하고, 우리는
구독 금액만 바꿔 청구하므로 빌링키 구조를 그대로 쓴다. 나중에 진짜 종량제로
바꾸는 것도 언제든 가능하다.

### Business 전용 기능의 근거

3배 가격의 근거는 기능 목록이 아니라 **고객 유형**이다.

> **Starter** — 내 브랜드 하나를 본다
> **Business** — 여러 브랜드를 책임진다 (대행사, 여러 라인을 가진 회사)

브랜드 다중 등록이 특히 중요하다. 대행사는 클라이언트가 5~10개고 각각
보고해야 하므로 브랜드 하나짜리 도구는 후보에도 못 든다. 그리고 대행사는
**우리 유통 채널**이 된다 — 한 곳을 잡으면 그 클라이언트들에게 소개된다.
1인 개발자에게 이보다 나은 판매 경로는 없다.

구현 비용도 거의 없다. 데이터 모델이 이미 `users → brands` 1:N이라 플랜 상수에
`maxBrands`를 추가하는 것이 전부다.

**원가를 지키는 방법:** 브랜드 3개에 각각 30질의를 주면 원가가 3배가 된다.
그래서 **질의 30개를 브랜드들이 나눠 쓴다**(브랜드 3개 × 각 10질의 = 총 30질의).
총 측정량이 같으므로 원가가 그대로이고 고객에게도 정직하다. 더 필요하면 질의
팩으로 늘린다.

### 넣지 않기로 한 것

**주 2회 측정 — 넣지 않는다.** 설계 ③의 변화 판정 원칙과 정면으로 충돌한다.

- 신뢰구간을 좁히는 것은 샘플 수지 측정 빈도가 아니다. 주 2회는 데이터
  포인트만 2배가 되고 각 측정의 정밀도는 그대로다
- 비교 횟수가 2배가 되므로 우연히 신뢰구간이 겹치지 않는 오탐도 2배가 된다.
  **비싼 요금제일수록 대시보드가 더 요동치게 된다**
- GEO는 주 단위로 움직이지 않는다. 콘텐츠를 올려도 AI 답변에 반영되는 데 몇
  주가 걸린다

"화살표를 아끼는 게 제품을 지킨다"고 정해놓고 돈을 더 받으려고 화살표를
남발하는 기능을 파는 셈이 된다.

**팀 계정 — 2단계로 미룬다.** 구현은 실질적인데(초대·권한·멀티테넌시) 고객이
돈을 더 내는 이유는 되지 않는다. 주 1회 보는 리포트 도구에서 시트 과금은 잘
통하지 않고, 소규모 팀은 로그인 하나를 돌려쓴다. 요청이 실제로 들어오면 그때
만든다.

## 기술 스택

| 층 | 선택 |
| --- | --- |
| 프레임워크 | Next.js 16.2.x (App Router) + React 19.2 + TypeScript |
| UI | Tailwind 4 + shadcn/ui |
| DB | Neon (Postgres) + Drizzle ORM |
| 인증 | Better Auth |
| 배치 | Trigger.dev |
| 결제 | 토스페이먼츠 (빌링키 정기결제) |
| 배포 | Vercel Pro |
| SERP 수집 | SerpApi (네이버 AI 브리핑 · Google AI Overviews) |

Next.js 16은 LTS이며 Turbopack이 기본 번들러다. 버전은 `latest`가 아니라
`16.2.x`로 고정한다.

### 백엔드 4종의 역할과 선택 근거

```
사용자 ──▶ [Next.js]
              ├─ Better Auth  누가 보는가 — 로그인·세션·권한
              ├─ Drizzle      DB와 대화 — 쿼리를 타입 안전하게
              │     ↓
              ├─ Neon         데이터 저장 — Postgres
              └─ Trigger.dev  오래 걸리는 일 — 주간 수집 300회
```

넷이 따로 필요한 이유는 **Vercel 서버리스 함수가 몇 분이면 강제 종료되기
때문**이다. 수집 한 번이 5~15분이라 웹 요청 안에서 처리할 수 없고, 별도 실행
환경이 필요하다.

| 도구 | 무료 티어 | 다음 단계 | 채택 근거 |
| --- | --- | --- | --- |
| **Neon** | 0.5GB · 100 CU-h · scale-to-zero 5분 | 종량제 $0.106/CU-h | 유휴 시 0원. Supabase 무료 티어는 7일 미사용 시 정지되어 초기에 치명적 |
| **Trigger.dev** | $5 크레딧 · 동시 20 · 스케줄 10 | Hobby $10 · 동시 50 | Inngest는 무료 동시 실행이 5뿐이고 다음 단계가 곧장 $99 |
| **Better Auth** | 무제한 (라이브러리) | — | Clerk은 B2B 조직 기능이 별도 $100/월. Better Auth는 조직 플러그인이 무료 |
| **Drizzle** | 무제한 | — | 집계·시계열 쿼리가 많아 SQL에 가까운 편이 유리. Prisma는 결국 raw SQL로 빠져나감 |

Better Auth는 라이브러리라서 우리 앱 안에서 돌고 사용자 데이터가 우리 Neon DB에
저장된다. 외부에 사용자를 맡기지 않으므로 비용도 종속도 없다.

**Supabase로 합치는 안은 검토 후 기각했다.** Pro($25)면 DB·인증·Realtime이
한 번에 오지만 **가장 어려운 조각인 잡 오케스트레이션을 대체하지 못한다.**
Edge Function도 시간 제한이 있어 15분 수집을 못 돌리므로 Trigger.dev가 그대로
필요하다. 돈을 더 내고 조각 하나만 줄이는 셈이다.

고객 10명 시점의 합계는 현재 조합이 약 28,000원, 같은 역할을 유명 상용
서비스로 바꾸면 약 349,000원이다. 기능적으로 얻는 것은 없다.

### 네이버 접근 경로 — 세 가지 중 하나만 안전하다

네이버는 이 제품의 차별점이자 최대 기술 리스크다. 경로를 명확히 못박아 둔다.

**① 네이버 오픈 API — 쓰지 않는다.**

[네이버 개발자센터](https://developers.naver.com/) 검색 API는 하루 25,000회
한도이고 초과·오남용 시 이용이 제한된다. 그런데 더 중요한 사실은 **이 API가
블로그·뉴스·카페·쇼핑 문서 검색만 돌려주고 AI 브리핑은 제공하지 않는다**는
점이다. 쓰면 계정 정지 리스크는 지면서 원하는 데이터는 못 얻는다.

**② 자체 스크래핑 — 하지 않는다.**

네이버는 robots.txt, rate limiting, JS 렌더링 의존, 캡챠, IP 차단의 다층 방어를
운영하며 2025년 AI 봇 크롤링을 전면 차단했다. 기술 난이도보다 심각한 것은
robots.txt 위반이 법적 분쟁에서 불리하다는 점이다. 그리고 차단당하는 순간
유료 고객의 서비스가 멈춘다.

**③ SerpApi — 이것을 쓴다.**

SerpApi는 검색 API와 별도로 [Naver AI Overview
API](https://serpapi.com/naver-ai-overview-api)를 제공하며, AI 브리핑을
`text_blocks` · `references` · `markdown`으로 구조화해 돌려준다.

핵심은 **리스크를 아웃소싱한다**는 것이다. 차단 대응은 SerpApi의 사업이지 우리
사업이 아니다. 우리 계정이 정지될 일도, 우리가 네이버와 다툴 일도 없다.

**경쟁사는 어떻게 하는가.** 외부에서 확인할 방법이 없다. 서드파티 API, 자체
스크래핑 인프라, 사람이 직접 확인 중 하나다. 세 번째를 흘려들으면 안 된다 —
OPTIGEO는 "Self 구독 · Hybrid · 전담 Turn-key"로 월 수백만원을 받으므로 사람이
붙어도 채산이 맞는다. **에이전시는 자동화가 막히면 사람으로 때울 수 있지만
99,000원 SaaS는 못 한다.** 자동 수집 경로 확보가 우리에겐 생존 조건이다.

**의존 리스크 완화:**

- 네이버가 막혀도 `Engine` 인터페이스 덕에 공급자 교체가 파일 하나 교체다
- `completeness` 기록으로 네이버 실패가 나머지 데이터를 오염시키지 않는다
- 약관에 명시한다 — "제3자 플랫폼 정책 변경 시 해당 엔진 측정이 중단될 수 있음"
- 대체 공급자 후보를 미리 확보한다 (ScraperAPI, Bright Data 등). 쓰지 않더라도
  막혔을 때 하루 만에 옮길 수 있어야 한다

1. **검색 툴 요금은 모델을 바꿔도 안 줄어든다.** 줄어드는 것은 토큰뿐이다.
   그래도 모델만 저가로 내리면 호출당 60% 이상 떨어진다 — 제품을 하나도 깎지 않고.

   나눠 쓰므로** 고객이 늘면 잠식된다 — 관측 대상이다.

**미확정(2단계 스모크 테스트에서 실측할 것):** 검색으로 딸려오는 본문 토큰 수.
위 계산은 8,000 토큰을 가정했으나 실제로는 5,000일 수도 20,000일 수도 있다.
**이것이 원가 추정의 가장 큰 불확실성이다.**

### 상한은 건수가 아니라 예산에서 역산한다

**"일 N건"을 먼저 정하면 안 된다.** 건당 원가가 고정이 아니기 때문이다 —
검색으로 딸려오는 본문 토큰이 질의마다 다르다(5,000~20,000). 건수만 세면
"상한은 지켰는데 청구서는 2.5배"가 나온다.

순서는 **월 손실 상한 → 건당 원가 → 일일 건수**다.

| 월 예산 | 월 건수(건당 100원) | 일일 상한 |
| --- | --- | --- |
| 5만원 | 500건 | 약 16건 |
| **10만원** | **1,000건** | **약 33건** |
| 20만원 | 2,000건 | 약 66건 |

**채택: 월 예산 10만원.** 다만 **초기값은 일 20건으로 보수적으로 잡고**, 2단계
실측이 나온 뒤 상향한다. 지금 33을 박으면 추정치 위에 짓는 것이다.

그리고 **두 겹으로 건다.**

1. **일일 건수 상한** — 남용·봇 방어용. `free_audits.ip_hash`로 센다
2. **월간 원가 예산 킬스위치** — 실제 토큰 사용량을 누적해 80%에서 알림,
   100%에서 진단 차단. **10만원을 실제로 보장하는 것은 이쪽이다.** 1번은 보조다

10만원 예산이면 Gemini 무료 grounding 티어(월 5,000건) 안에 여유롭게 들어온다
(1,000건 × 3호출 = 3,000).

> 킬스위치가 있어야 손익분기를 통제할 수 있다.

### SerpApi 가입 시점과 업그레이드 기준

**유료 플랜을 여는 시점에 미리 가입한다. 고객이 0명이어도.** 고객이 새벽에
결제하면 그 순간 첫 수집이 돌아야 하는데, SerpApi가 없으면 네이버와 Google
AIO가 통째로 실패해 첫인상이 "엔진 2개 수집 실패" 배지가 된다. 월 35,000원은
그에 비하면 싼 보험이다.

무료 진단만 배포하는 1단계에서는 여전히 불필요하다.

**Automatic Early Renewal을 켠다.** 쿼터를 다 쓰면 하드 스톱이 아니라 조기
갱신된다. 예상 못 한 청구보다 고객 서비스 중단이 훨씬 비싸다.

업그레이드 판단은 **고객 수가 아니라 예상 호출량으로 한다.** Starter와
Business의 소비량이 3배 차이나므로 고객 수는 기준이 될 수 없다.

```
고객 1명의 월 SERP 호출 = 질의수 × 2 SERP엔진 × 2샘플 × 4.3주
  Starter  (10질의) = 172건/월
  Business (30질의) = 516건/월

예상 월 호출량 = Σ(고객별 호출량)
  → 80% 도달 시 알림
```

| 플랜 | 건수 | 감당 가능 |
| --- | --- | --- |
| Starter $25 | 1,000건 | Starter 5명 또는 Business 1명 |
| Developer $75 | 5,000건 | Starter 29명 또는 Business 9명 |
| Production $150 | 15,000건 | |

**Business 두 번째 계약이 곧 업그레이드 시점이다**(2명 = 1,032건 > 1,000건).
업그레이드는 차액만 결제하고 갱신일이 유지되며 즉시 반영된다.

## 설계안 ① — 시스템 구조와 모듈 경계

```
app/          Next.js 라우트 (랜딩·무료진단·대시보드·설정·결제)
  ↓
collection/   수집 오케스트레이션 (Trigger.dev) — 스케줄·재시도·동시성
  ↓        ↘
engines/      detection/    브랜드 언급 판정 (순수 함수)
엔진 어댑터        ↓
              stats/        집계·신뢰구간
```

### engines/

외부 엔진 하나당 파일 하나. 전부 같은 인터페이스를 구현한다.

```ts
interface Engine {
  id: 'chatgpt' | 'gemini' | 'naver' | 'google_aio'
  tier: 'llm' | 'serp'          // 샘플 수 차등의 근거
  run(query: string): Promise<EngineAnswer>
}

interface EngineAnswer {
  text: string
  citations: { url: string; title: string }[]
  raw: unknown                   // 원본 보관 (재판정용)
}
```

엔진 추가가 파일 하나 추가로 끝난다. Claude·Perplexity를 나중에 넣을 때 다른
모듈을 건드리지 않는다. 네이버 공급자를 SerpApi에서 다른 곳으로 옮길 때도
마찬가지다.

### detection/

답변 텍스트에서 브랜드 언급을 판정한다. 외부 호출이 없는 순수 함수다.

```ts
detectMentions(answer: EngineAnswer, brand: BrandProfile): Detection
```

1차는 정규식·문자열 매칭(브랜드명 + 표기 변형 + 흔한 오탈자), 2차는 1차
통과분만 LLM으로 맥락·감성·언급 순서를 판정한다. 1차에서 걸러내는 것이 원가
절감의 핵심이며, 순수 함수이므로 실제 API 없이 테스트할 수 있다.

### collection/

Trigger.dev 잡. 질의 × 샘플 × 엔진으로 팬아웃하고 재시도와 동시성 제한을
담당한다. 비즈니스 로직은 두지 않고 오케스트레이션만 한다.

### stats/

판정 결과로 언급률·신뢰구간·경쟁사 대비 점유율을 계산한다. 순수 함수다.

### 핵심 원칙

외부 I/O가 있는 곳(`engines`, `collection`)과 판단 로직(`detection`, `stats`)을
분리했다. 이 제품의 최대 리스크가 측정 신뢰도이기 때문이다. 판정 로직이 순수
함수여야 저장해둔 실제 답변으로 회귀 테스트를 돌릴 수 있고, 판정 기준을 바꿨을
때 과거 데이터로 재판정해 결과 변화를 확인할 수 있다. `EngineAnswer.raw`를
보관하는 이유도 같다.

## 설계안 ② — 데이터 모델과 수집 파이프라인

```
users (Better Auth)
  └─ subscriptions       plan, status, billingKey, currentPeriodEnd,
                         queryPacks★
  └─ brands              name, aliases[], category, competitors[], queryQuota

brands
  └─ queries             text, isActive, source(generated|custom)
  └─ collection_runs     planSnapshot★, completeness, status,
                         startedAt, finishedAt
       └─ answers        queryId, engineId, sampleIndex, text, citations, raw★
            └─ detections  subject, mentioned, position, sentiment,
                           detectorVersion★

free_audits              email, brandName, result, ipHash, variant, createdAt
```

★ 표시한 필드가 이 설계의 핵심이다.

- **`planSnapshot`** — 수집 당시의 플랜 설정(질의 수·샘플 수·엔진)을 통째로
  박제한다. 이것이 없으면 "지난달 대비 상승"이 실제 상승인지 조건 변경인지
  구분할 수 없고 시계열 전체가 무의미해진다.
- **`answers.raw`** — 원본을 버리지 않는다. 판정 로직 개선 후 과거 데이터를
  재판정할 수 있다. 용량은 브랜드당 월 1~2MB로 무시할 수준이다.
- **`detectorVersion`** — 어느 버전 로직이 매긴 판정인지 기록한다. 재판정 후
  숫자가 달라진 이유를 고객에게 설명할 수 있다.
- **`queryPacks`** — 구매한 질의 팩 수. 질의 한도는
  `PLANS[plan].maxQueries + queryPacks × 10`으로 계산한다.

`brands.queryQuota`는 Business에서 브랜드 3개가 총 질의 한도를 나눠 쓰기 위한
필드다. 합이 계정 한도를 넘지 않도록 검증한다.

### 플랜 설정은 코드 상수

```ts
const PLANS = {
  free: {
    maxBrands: 1, maxQueries: 3, maxCompetitors: 3,
    engines: ['chatgpt', 'gemini'],
    samples: { llm: 1, serp: 0 },
    historyMonths: 0, csvExport: false,
  },
  starter: {
    maxBrands: 1, maxQueries: 10, maxCompetitors: 3,
    engines: ['chatgpt', 'gemini', 'naver', 'google_aio'],
    samples: { llm: 3, serp: 2 },
    historyMonths: 3, csvExport: false,
  },
  business: {
    maxBrands: 3, maxQueries: 30, maxCompetitors: 10,
    engines: ['chatgpt', 'gemini', 'naver', 'google_aio'],
    samples: { llm: 3, serp: 2 },
    historyMonths: null, csvExport: true,   // null = 무제한
  },
} as const

const QUERY_PACK_SIZE = 10
```

DB가 아닌 상수로 두면 티어 추가가 한 줄로 끝나고 마이그레이션이 필요 없다.

### 스케줄은 브랜드당 1개가 아니라 전체 1개다

Trigger.dev 무료 티어의 스케줄 한도는 10개다. **브랜드마다 스케줄을 만들면 고객
10명에서 막힌다.**

```
❌ 브랜드마다 스케줄 1개        → 10명이 상한
✅ 매일 도는 스케줄 1개가
   "오늘 수집할 브랜드"를 골라 실행  → 무제한
```

후자가 한도와 무관하게 더 나은 설계이기도 하다. 브랜드는 가입 요일을 기준으로
주기가 정해지므로 수집 부하가 요일별로 자연히 분산된다.

### 수집 파이프라인

```
Trigger.dev 스케줄 (매일 1회) → 오늘 수집할 브랜드 선별 → 브랜드별로 실행
  1. 플랜 로드 → planSnapshot 생성 → collection_run 시작
  2. 팬아웃: queries × engines × samples
     질의당 (2 LLM × 3) + (2 SERP × 2) = 10회
     Starter  10질의 → 주 100회
     Business 30질의 → 주 300회
     각 실행이 독립 서브태스크 → 개별 재시도, 동시성 제한
  3. answers 저장 (원본 포함)
  4. 판정 배치 — 1차 정규식 필터 → 2차 LLM 배치 호출
  5. 집계 → 언급률 · 신뢰구간 · 경쟁사 대비
  6. run 완료 → 주간 리포트 메일
```

판정을 수집에서 분리한 것은 의도적이다. 원본이 남아 재판정이 가능하고, LLM
판정을 배치로 묶어 원가를 낮출 수 있으며, 판정이 실패해도 수집 데이터는
살아남는다. 한 번 놓친 시점의 AI 답변은 다시 만들 수 없다.

동시성 제한은 필수다. 고객 10명이면 주 1,000~3,000회 실행이므로 한꺼번에
던지면 각 엔진의 rate limit에 걸린다. Trigger.dev의 동시성 제어를 엔진별로 나눠
건다.

### "주 1회 수집"의 정확한 의미

일주일에 **걸쳐** 모으는 것이 아니라, 일주일에 **한 번** 한 시점에 몰아서
300회를 재는 것이다.

```
❌ 오해:  월 ─ 화 ─ 수 ─ 목 ─ 금 ─ 토 ─ 일    7일간 조금씩
✅ 실제:  월(5~15분에 300회) ····· 다음 월(300회)
```

**수집 한 번이 완결된 데이터 포인트 하나**다. Cited Rate의 신뢰구간은 일주일간의
변동이 아니라 **300회 측정 사이의 편차**를 뜻한다. 이 구분이 다음 절의 근거가
된다.

### 가입 즉시 첫 수집을 돌린다

스케줄만 두면 화요일에 결제한 고객은 다음 월요일까지 아무것도 못 본다. 무료
진단에서 20초 만에 결과를 보여준 뒤 돈을 받고 6일을 기다리게 하는 셈이라
환불 사유가 된다.

```
결제 성공
  → 즉시 collection_run 트리거 (스케줄을 기다리지 않음)
  → 진행 화면: "첫 측정을 진행하고 있습니다... (127/300)"
  → 5~15분 후 대시보드 완성
  → 이후 가입 요일 기준 주 1회
```

새로 만들 것은 거의 없다. 진행 화면은 무료 진단의 Realtime 컴포넌트를 그대로
쓰고, 수집 파이프라인도 동일하다. **트리거가 스케줄이 아니라 결제 이벤트일
뿐이다.**

첫 수집의 결과물은 정식 주간 수집과 완전히 같다. 다만 비교할 지난주가 없으므로
▲▼를 표시하지 않고 "다음 주부터 변화를 추적합니다"로 대체한다. 설계 ③의 변화
판정 원칙과 일관된다.

### SERP 2샘플은 시간대를 나눠 호출한다

**SerpApi는 결과를 1시간 캐시하고 캐시 조회는 무료다.** 두 샘플을 연속으로
호출하면 같은 캐시가 두 번 나온다. 비용은 1회분이지만 정보도 1회분이라 샘플
2회의 의미가 사라진다.

→ SERP 샘플은 오전·오후로 나눠 호출한다. AI 브리핑도 시점에 따라 바뀌므로
이렇게 해야 진짜 2샘플이 된다. LLM 엔진은 캐시가 없으므로 해당 없다.

### 무료 진단 플로우

3질의 × 2엔진 × 1샘플 = 6호출로 10초 안팎이 걸린다. Vercel 함수 타임아웃 안에서
동기 처리하면 위험하므로 Trigger.dev 잡으로 던지고 Realtime으로 진행률을
스트리밍한다.

```
브랜드명 입력 → [Turnstile · 캐시 조회 · 예산 확인] → 잡 시작
  "ChatGPT에 물어보는 중... (2/3)"
  "Gemini에 물어보는 중... (3/3)"
  → 결과 표시 → 이메일 입력해야 전체 리포트 열람
```

**대괄호 안의 세 관문은 잡을 시작하기 전에 통과해야 한다.** 잡이 시작되는
순간 돈이 나가므로, 방어는 전부 그 앞에 있어야 한다.

진행 문구 자체가 "이 도구가 진짜로 AI에 물어보고 있다"는 증거로 작동한다.

무료 진단이 SERP를 쓰지 않는 것은 원가 억제와 업셀 축 확보를 겸한다.

**질의는 3개 고정이다.** 2개가 아니라 3개인 이유는 원가가 아니라 설득력이다.

- 분모가 작을수록 Cited Rate는 숫자 노릇을 못 한다. 1질의 × 2엔진이면 분모가
  2라서 값이 0%·50%·100% 셋뿐이고, Wilson 95% 구간이 **9~91%**다. 정보가 없다.
  (3질의 × 2엔진 = n6이면 19~81%. 여전히 넓지만 화면에 쓸 말이 생긴다.)
- 무료 진단은 샘플 1회라 **비결정성이 그대로 노출된다.** 무료 툴은 사람들이 두 번
  돌려본다. n이 작으면 두 번째에 값이 뒤집혀 "고장난 툴"이 된다.
- **전환을 만드는 것은 비율이 아니라 패턴이다.** "3개 중 2개에서 경쟁사만 나온다"는
  반박하기 어렵지만, 답변 하나는 "그 질문이 이상했겠지"로 넘어간다.
  한 번은 우연이고, 반복은 문제다. 3이 반복의 최소 개수다.

**질의 3개는 서로 다른 의도 축이어야 한다** (일반 추천 / 속성 한정 / 비교형).
유사 질의 3개를 만들면 답변도 셋 다 비슷해져 데이터 포인트가 1개짜리가 된다.
개수보다 이쪽이 중요하다.

**화면에는 퍼센트보다 실제 답변을 보여준다.** 이 n에서 퍼센트는 거짓 정밀도다.
"ChatGPT는 A사·B사를 추천했고 귀사는 없습니다"가 통계적으로도 정직하고
심리적으로도 강하다. 3질의는 이 형태에서 더 강해진다 — 이름이 연속으로 없는 게 보인다.

**모델은 무료 진단 전용으로 저가 모델을 쓴다.** 검색 툴 요금은 모델과 무관하게
붙지만 토큰이 크게 줄어 호출당 60% 이상 절감된다(비용 구조 절 참고). 진단은
리드 수집용이라 유료 측정만큼의 정확도가 필요 없다.

### 무료 진단 남용 방지

> **최초 설계의 오류(2026-07-29 정정):** 남용 방지를 "이메일 인증 + 브랜드당
> 월 1회 + IP 일일 상한"으로 적어 뒀는데, 위 플로우는 **이메일을 받기 전에 잡을
> 시작한다.** 즉 이메일 게이트는 돈이 나간 **뒤에** 걸리는 리드 수집 장치였지
> 비용 방어가 아니었다. 실제 방어는 IP 상한 하나뿐이었고 그건 프록시로 뚫린다.

**공격의 경제학부터 본다.**

| | 공격자 비용 | 우리 비용 |
| --- | --- | --- |
| 손으로 50번 | 1시간 | 5,000원 |
| 스크립트+프록시로 10,000번 | 거의 0 | 100만원 |

**차이를 만드는 것은 자동화 여부다.** 사람이 손으로 하는 것은 위협이 아니다 —
실수로 몇 번 더 돌린 정상 사용자와 구분도 안 된다.

그리고 **최대 손실은 예산 킬스위치가 이미 10만원에 묶는다.** 그러므로 방어의
목적은 손실 방지가 아니다. 진짜 피해는 이것이다.

> 공격자가 아침에 예산을 다 태움 → 그달 남은 29일간 **진짜 잠재고객이 진단을
> 못 돌림** → 리드 0

**방어의 목적은 남은 예산을 진짜 사람에게 쓰는 것이다.**

효과÷비용 순으로:

1. **Cloudflare Turnstile** — 무료, 대부분 사용자에게 보이지 않는다. 자동화만
   막으면 위협의 대부분이 사라진다. **이것 하나가 나머지 전부보다 효과가 크다.**
2. **브랜드+카테고리 캐시(7일)** — 같은 브랜드 재요청은 API를 안 태운다.
   `audits_brand_created_idx`가 이미 있다. 정당한 중복도 아끼므로 순이득이고,
   공격자는 매번 다른 브랜드명을 넣어야만 비용을 태울 수 있다.
3. **월 예산 킬스위치** — 다른 게 다 뚫려도 손실이 멈추는 지점.
4. **IP 해시 일일 상한** — `audits_iphash_created_idx` 이미 있음.

**채택하지 않은 것: 점진적 마찰**(1회차 무마찰 → 2회차 Turnstile → 3회차 이메일).
한국 사무실은 대부분 공유 IP(NAT)다. **대행사에서 마케터 3명이 각자 담당 브랜드를
돌리면 세 번째가 막힌다** — 그 대행사가 우리가 가장 원하는 고객이다.
오탐 비용이 방어 이득보다 크다.

**이메일 게이트 위치는 환경변수 플래그로 전환 가능하게 만든다.**

- 기본값 = 지금 위치(실행 후). 트래픽이 예산에 못 미치는 동안은 마찰이 순손해다
- 트래픽이 예산을 채우기 시작하면 **실행 전으로 옮긴다.** 그때는 예산이 병목이므로
  인증을 통과한 사람에게만 쓰는 편이 리드를 더 많이 가져온다(인증률 15% 가정 시
  같은 10만원으로 방문 6,600명까지 소화 — 실행 후 게이트는 1,000명에서 끝난다)
- 어차피 만들 이메일 인증 컴포넌트의 **호출 위치만 바꾸는 일**이다. 설계 단계에서
  그렇게 잡아 두면 플래그 하나로 전환된다. 터진 뒤에 코드를 고치면 늦는다

상한 소진 시 에러가 아니라 대기 등록으로 받아 리드는 확보한다.

## 설계안 ③ — 측정·판정 로직

### 2단계 판정: 1차는 넓게, 2차가 걸러낸다

```
답변 텍스트
   ↓
1차 — 문자열/별칭 매칭        recall 우선 (놓치지 않기)
   ↓  통과분만
2차 — LLM 구조화 판정          precision 확보 (맞는지 확인)
   ↓
Detection
```

1차를 정밀하게 만들려는 유혹을 참아야 한다. 1차의 임무는 "여기 뭔가 있을 수
있다"까지고 판단은 2차가 한다. 이렇게 나누는 이유는 원가다. 전체 답변의
70~80%가 1차에서 탈락하므로 LLM 호출이 그만큼 줄어든다.

### 1차 — 별칭 매칭

```ts
interface BrandProfile {
  canonical: string        // "무신사"
  aliases: string[]        // ["MUSINSA", "Musinsa", "무신사스탠다드", "무탠다드"]
  ambiguous: boolean       // 일반어와 겹치는가
}
```

별칭은 온보딩에서 자동 생성 후 고객이 편집한다. 한글·영문 표기, 띄어쓰기 변형,
커뮤니티 축약어(무신사스탠다드 → 무탠다드), 흔한 오탈자까지 잡아야 한다.

`ambiguous` 플래그가 필요한 이유는 브랜드명이 일반어와 겹치는 경우가 실제로 많기
때문이다. "소나기", "달차", "미미" 같은 이름은 문자열만으로 브랜드인지
일반명사인지 알 수 없다. 이 플래그가 켜지면 2차 판정을 무조건 거치고, 꺼져
있으면 명백한 케이스는 2차를 건너뛰어 원가를 아낀다.

### 2차 — LLM 구조화 판정

1차 통과분을 배치로 묶어 구조화 출력으로 받는다.

```ts
{
  isBrandReference: boolean   // 동음이의어 배제
  position: number | null     // 답변에서 몇 번째로 언급된 브랜드인가
  sentiment: 'recommended' | 'neutral' | 'negative'
  context: string             // 한 줄 요약 (고객에게 그대로 노출)
}
```

**`position`이 이 제품에서 가장 값진 필드다.** "언급되었다"보다 "첫 번째로
추천되었다"가 훨씬 중요하다. 소비자는 AI가 처음 꺼낸 이름을 본다. 3번째 언급과
1번째 언급은 사업적으로 완전히 다른 얘기다.

판정 모델은 저렴한 것부터 시작한다(Claude Haiku 4.5 등). 단, 모델을 고르기 전에
정확도를 재야 한다.

### 골드 라벨 세트 — 검증하지 않은 숫자는 주장일 뿐이다

고객에게 "당신의 Cited Rate는 34%입니다"라고 말한다. 그게 맞는지 우리가 어떻게
아는가. 판정기가 틀리면 숫자 전체가 거짓말이고, 고객은 자기 브랜드니까 금방
알아챈다 — "이 답변에 우리 나오는데 왜 미포함이야?"

```
실제 수집한 답변 200개를 손으로 라벨링
  → 판정기 정확도 측정 (precision / recall)
  → 목표: recall 95%+ (놓치지 않기가 더 중요)
  → 판정 로직이나 모델을 바꿀 때마다 이 세트로 회귀 검증
```

라벨링 200개는 반나절이면 된다. 이걸 건너뛰면 제품의 모든 숫자가 근거 없는
주장이 된다. 설계 ①에서 `detection`을 순수 함수로, `answers.raw`를 원본
보관으로 잡은 이유가 전부 이걸 가능하게 하기 위해서였다.

포트폴리오 관점에서도 가장 강력한 소재다. "LLM API를 붙였습니다"는 누구나
하지만, "비결정적 출력의 측정 신뢰도를 라벨 세트로 검증했습니다"는 신입
지원자에게서 보기 드문 얘기다.

### 지표 정의

| 지표 | 정의 |
| --- | --- |
| **Cited Rate** | 우리 브랜드가 언급된 응답 / 전체 응답 — **대표 지표** |
| **First-Mention Rate** | 첫 번째로 언급된 응답 / 전체 응답 |
| **Share of Voice** | 우리 언급 수 / (우리 + **등록된** 경쟁사 언급 수) |
| **질의별 상세** | 어떤 질문에서 안 나오는지 — 실행 가능한 정보 |

제품명이 Cited이므로 Cited Rate가 대표 지표다. 이름과 지표가 일치해 설명이
필요 없다.

#### ★ Share of Voice는 고객 설정에 의해 왜곡된다 (2026-07-29 추가)

이 지표에는 다른 셋과 다른 성질이 있다. **분모가 고객이 등록한 경쟁사 목록에
의존한다.** 판정기는 별칭을 모르는 브랜드를 셀 수 없으므로 "답변에 등장한 모든
브랜드"를 분모로 쓰는 것은 **애초에 계산 불가능**하다.

그 결과 **경쟁사를 적게 등록할수록 우리 SoV가 올라간다.** 지표가 측정 대상이
아니라 설정에 의해 움직인다. 고객이 의도적으로 조작할 수도 있고, 몰라서 2곳만
등록해 놓고 "우리가 62%"라고 믿을 수도 있다. 후자가 더 위험하다 — 우리가 거짓
정보를 제공한 것이 된다.

**지켜야 할 규칙 넷.**

1. **경쟁사 0개면 SoV를 계산하지 않는다.** `n = 0`("측정 없음")을 돌려준다.
   순진하게 계산하면 `우리/(우리+0)` = **항상 100%**가 나오는데, 이건 측정
   결과가 아니라 설정 누락이다. 화면에 100%를 띄우면 그건 거짓말이다.
   (`src/lib/stats/metrics.ts`가 이렇게 구현돼 있다. 되돌리지 말 것.)
2. **화면에 SoV를 단독으로 노출하지 않는다.** 반드시 **경쟁사 수를 병기**한다.
   "62% (경쟁사 2곳 기준)"과 "62% (경쟁사 8곳 기준)"은 전혀 다른 주장이다.
3. **경쟁사 집합이 다른 기간끼리 SoV를 비교하지 않는다.** 엔진 구성이 다른
   주끼리 비교하지 않는 것과 **정확히 같은 이유**다 — 숫자가 움직인 원인이
   실제 변화인지 설정 변경인지 구별할 수 없다. `collection_runs.planSnapshot`에
   경쟁사 집합을 함께 박제하고, 집합이 바뀐 구간의 SoV 화살표는
   `incomparable`로 처리한다.
4. **온보딩에서 경쟁사 3곳 이상을 권한다.** 그 미만이면 SoV를 대표 지표가
   아니라 "참고값"으로 낮춰 표시한다.

**중장기 개선:** 2차 LLM 판정이 이미 답변 전문을 보므로, **미등록 브랜드 후보를
함께 수집**할 수 있다. "미등록 브랜드가 N회 등장했습니다"를 병기하면 고객이
왜곡의 크기를 직접 볼 수 있고, 경쟁사 등록을 유도하는 장치도 된다.

### 신뢰구간은 Wilson으로 계산한다

교과서적 정규근사(Wald)를 쓰면 안 된다. 언급률이 0%나 100%일 때 완전히 망가지기
때문이다.

작은 브랜드는 실제로 0%가 자주 나온다. Wald로 계산하면 `0% ± 0%p`가 나오는데
이건 "확실히 0%다"라는 뜻이 되어 버린다. 90회 시행에서 0번과 10,000회에서 0번은
전혀 다른 정보인데 구분이 안 된다.

**Wilson score interval**은 이 경우를 정상적으로 처리한다. 90회 시행에 0번이면
대략 `0% ~ 4.1%`가 나오고, 이게 정직한 표현이다.

```
center     = (p̂ + z²/2n) / (1 + z²/n)
halfwidth  = z/(1+z²/n) × √( p̂(1-p̂)/n + z²/4n² )
```

### 변화 판정 — 겹치면 변화가 아니다

> 두 주의 신뢰구간이 겹치지 않을 때만 유의미한 변화로 표시한다. 겹치면
> "변화 없음(측정 범위 내)"으로 쓴다.

노이즈를 변화로 보고하는 순간 신뢰를 잃는다. 대시보드가 매주 요동치는데 실제로는
아무 일도 없었다면 고객은 두 달 안에 해지한다. 화살표를 아끼는 게 제품을 지킨다.

이 원칙이 "주 2회 측정"을 상위 요금제 기능에서 제외한 근거이기도 하다.

### 재판정 정책

`detectorVersion`이 올라가면 과거 답변을 재판정한다.

- 기존 `detections`를 삭제하지 않고 새 버전 판정을 추가한다 (감사 추적)
- 대시보드는 최신 버전 기준으로 표시한다
- 지표가 유의미하게 바뀌면 고객에게 공지한다. 숨기면 나중에 더 큰 문제가 된다

## 설계안 ④ — 화면 구성과 사용자 플로우

### 전환 퍼널

```
랜딩 (브랜드명 입력)
   ↓
진행 화면 (10초 안팎, Realtime 진행률)
   ↓
결과 — 증거와 순위는 즉시 공개
   ↓
이메일 입력 → 전체 지표 (엔진별·질의별·경쟁사 전체)
   ↓
가입 → 온보딩 → 결제
```

### 무료 진단 결과 화면 — C → B → A

이 제품에서 전환이 일어나는 유일한 화면이다. 기다린 방문자의 첫 질문은
"이거 진짜야?"이므로 **첫 임무는 충격이 아니라 신뢰**다.

```
[헤드라인]  무신사 · Cited Rate 12%        ← 한 줄, 작게
C.  증거      실제 AI 답변 원문 2~3개
B.  순위      AI가 실제로 답한 브랜드 순위표  (감정 정점)
━━━━━━━ 이메일 게이트 ━━━━━━━
A.  전체 지표  엔진별 · 질의별 · 경쟁사 전체 · 신뢰구간 → 구독
```

순서의 근거:

- **C(증거)가 먼저인 이유** — 숫자와 순위는 둘 다 반박 가능하다("그 숫자 어떻게
  잰 건데?"). AI 답변 원문은 반박할 수 없고, 방문자가 ChatGPT를 직접 열어
  검증할 수 있다. 신뢰가 먼저 서야 나머지가 작동한다.
- **B(순위)가 두 번째인 이유** — 순위의 감정적 충격은 데이터를 믿는 만큼만
  커진다. C 다음에 와야 정점을 찍는다.
- **A(전체 지표)가 마지막인 이유** — 정리된 숫자는 기억에 남는 앵커이자
  "매주 추적해 드립니다"로 넘어가는 다리다.

이메일 게이트는 A 앞에 둔다. 방문자는 이메일 없이도 진짜 가치(증거 + 순위)를
얻고, 게이트 뒤의 것은 실제로 추가 정보다. 정직한 거래라 반감이 적다.

**이 순서는 가설이지 사실이 아니다.** `free_audits.variant`에 노출한 순서를
기록하고 전환 결과를 함께 남긴다. 방문자 200명이면 데이터로 결론이 난다.
"추측하지 말고 측정하라"는 제품을 추측으로 만들 수는 없다.

### 온보딩 — 이탈이 가장 많이 나는 구간

"추적할 질의를 입력하세요"라고 하면 그 자리에서 나간다. 질문을 생각해내는
건 고객의 일이 아니다.

```
1. 브랜드명 + 카테고리 입력          ← 고객이 하는 유일한 입력
2. 별칭 자동 생성 → 확인/편집        "무신사, MUSINSA, 무탠다드 맞나요?"
3. 질의 자동 생성 → 확인/편집        체크박스로 끄고 켜기
4. 경쟁사 자동 추천 → 확인/편집      진단 결과에 자주 나온 브랜드
5. 결제
6. 첫 측정 진행 화면 (5~15분)       무료 진단과 같은 Realtime 컴포넌트
```

전부 "생성 후 확인" 구조다. 고객은 빈칸을 채우는 게 아니라 이미 채워진 걸
고친다. 심리적 부담이 완전히 다르다. 무료 진단을 이미 돌렸다면 2~4번은 그
결과를 그대로 재사용한다.

Business는 브랜드를 3개까지 등록하므로 온보딩이 브랜드 단위로 반복되고, 질의
한도를 브랜드별로 배분하는 화면이 하나 더 붙는다.

### 대시보드 — 실행 가능한 정보를 위로

```
┌─ Cited Rate ─────────────────────────────┐
│  34%  (29% ~ 40%)        ▲ 지난주 대비    │
│  300회 시행 · 신뢰구간 95%                 │
└──────────────────────────────────────────┘

┌─ 지금 조치할 것 ──────────────────────────┐
│  이 5개 질문에서 전혀 언급되지 않습니다     │
│  · "가성비 러닝화 추천"        0/10        │
│  · "발볼 넓은 사람 운동화"      0/10        │
└──────────────────────────────────────────┘

┌─ 경쟁사 대비 ────┐  ┌─ 엔진별 ──────────┐
│ 경쟁사A    71%   │  │ ChatGPT     42%   │
│ 우리       34%   │  │ Gemini      31%   │
│ 경쟁사B    22%   │  │ 네이버      28%   │
└─────────────────┘  │ Google AIO  35%   │
                     └───────────────────┘

┌─ 추이 (12주) ────────────────────────────┐
│  신뢰구간을 띠로 함께 표시                  │
└──────────────────────────────────────────┘
```

"지금 조치할 것"을 두 번째에 놓은 건 의도적이다. "우리가 34%다"는 알아도 할 일이
없다. "이 질문들에서 아예 안 나온다"는 콘텐츠를 어디에 써야 할지 알려준다.
**고객이 매주 다시 들어올 이유는 숫자가 아니라 할 일이다.**

추이 차트에는 신뢰구간을 띠로 같이 그린다. 선 하나만 그리면 노이즈가 추세처럼
보인다.

Business는 상단에 브랜드 전환 셀렉터가 붙고, 각 카드에 CSV 내보내기 버튼이
붙는다. 대행사가 클라이언트 리포트에 넣어야 하기 때문이다.

### 첫날 대시보드 — 5개 중 4개가 완전하다

가입 즉시 수집을 돌리므로 첫 화면이 비어 있지 않다.

| 카드 | 첫날 | 이유 |
| --- | --- | --- |
| Cited Rate + 신뢰구간 | ✅ 완전 | 300회 시행 기반 |
| 지금 조치할 것 | ✅ 완전 | 질의별 0/10 |
| 경쟁사 대비 | ✅ 완전 | |
| 엔진별 | ✅ 완전 | |
| 추이 차트 | 점 1개 | 2주차부터 선이 생김 |
| ▲▼ 변화 | ❌ 없음 | 비교할 지난주가 없음 |

상단에 상태를 명시한다.

```
✓ 첫 측정 완료 · 300회 시행
  다음 월요일부터 주간 변화를 추적합니다
```

### 화살표 규칙

- 신뢰구간이 겹치지 않을 때만 `▲` `▼` 표시
- 겹치면 `— 변화 없음` (회색)
- 툴팁으로 "측정 범위 내 변동입니다" 설명

## 설계안 ⑤ — 오류 처리와 테스트 전략

### 부분 실패를 허용하되 조용히 넘어가지 않는다

가장 흔한 장애는 엔진 4개 중 1개가 죽는 것이다. 두 가지 잘못된 선택지가 있다.

- 주간 수집 전체를 버린다 → 그 주 데이터가 영영 사라진다. AI 답변은 소급 수집이
  불가능하다
- 남은 3개로 계산해 그냥 보여준다 → 지난주는 4개 엔진, 이번주는 3개 엔진이 되어
  숫자가 떨어진 이유가 실제 하락인지 엔진 누락인지 알 수 없다

둘 다 안 된다. **부분 데이터는 저장하되 완전성을 기록한다.**

```ts
// Business 30질의 기준
collection_runs.completeness = {
  chatgpt:    { attempted: 90, succeeded: 90 },
  gemini:     { attempted: 90, succeeded: 88 },
  naver:      { attempted: 60, succeeded: 0  },  // 장애
  google_aio: { attempted: 60, succeeded: 60 },
}
```

- 완전성이 90% 미만이면 대시보드에 배지를 붙인다 — "네이버 수집 실패, 3개 엔진 기준"
- 시계열 차트에서 해당 주를 점선으로 그린다. 숨기지도, 실선으로 속이지도 않는다
- 변화 판정(▲▼)은 엔진 구성이 다른 주끼리는 하지 않는다

`planSnapshot`과 같은 원칙이다. 비교 가능성을 지키는 게 숫자를 채우는 것보다
중요하다.

### 장애 유형별 대응

| 장애 | 대응 |
| --- | --- |
| 엔진 호출 실패 | Trigger.dev 지수 백오프 3회. 429는 더 긴 대기. 400류는 즉시 포기 후 기록 |
| SerpApi 쿼터 소진 | Automatic Early Renewal이 켜져 있으면 조기 갱신되어 멈추지 않는다. 80% 도달 시 알림. 갱신이 실패한 경우에만 SERP를 스킵하고 LLM은 계속 |
| **네이버 경로 차단** | 공급자 교체(`Engine` 구현체 교체). 그동안 completeness에 기록하고 배지 표시 |
| 판정 LLM 실패 | `detections`에 미판정으로 남긴다. 원본이 있으므로 데이터 손실 없음 — 나중에 재판정 |
| 결제 실패 | 유예 기간 후 수집 중단. 과거 데이터는 유지해 재구독 시 시계열이 이어진다 |
| 무료 진단 남용 | Turnstile + 브랜드 캐시 + 월 예산 킬스위치 + IP 일일 상한. **잡 시작 전에 전부 통과해야 한다** — 이메일 게이트는 실행 뒤라 비용 방어가 아니다("무료 진단 남용 방지" 절) |
| **무료 진단 예산 소진** | 에러가 아니라 대기 등록으로 받는다. 관리자에 알림 — 80%에서 미리 온다 |

판정 실패가 데이터 손실이 아니라는 게 설계 ②의 배당금이다. 수집과 판정을
분리하고 원본을 보관했기 때문에 판정 단계 장애는 언제든 복구 가능한 일이 된다.

### 테스트 전략

원칙은 하나다. **순수 함수는 단위 테스트, I/O는 픽스처.** 설계 ①에서 모듈을 나눈
이유가 여기서 회수된다.

**1. `detection/` — 골드 라벨 회귀 테스트 (가장 중요)**

설계 ③의 라벨 200개가 그대로 테스트 스위트가 된다.

```
CI에서 매번 실행
  → recall < 95% 또는 precision < 90% 이면 빌드 실패
```

판정 로직이나 모델을 바꿀 때마다 자동 검증된다. 이 제품에서 회귀가 나면 안 되는
유일한 곳이고, 여기만 지키면 나머지 버그는 복구 가능하다.

**2. `stats/` — 경계값 단위 테스트**

Wilson interval은 경계에서 틀리기 쉽다. 반드시 포함할 케이스:

- `n=90, k=0` → 0% ~ 4.1% (0%가 아님)
- `n=90, k=90` → 95.9% ~ 100%
- `n=1` → 구간이 거의 전 범위
- 구간 겹침 판정 — 겹칠 때 "변화 없음"이 나오는지

**3. `engines/` — 저장된 응답으로 계약 테스트**

실제 API를 부르지 않는다. 수집해둔 실제 응답을 픽스처로 두고 파싱을 검증한다.
엔진의 응답 스키마가 바뀌면 여기서 잡힌다.

별도로 주 1회 스모크 테스트를 돌려 각 엔진에 실제 1회 호출한다. 스키마 변경이나
인증 만료를 조기에 발견하기 위해서고 비용은 무시할 수준이다. **네이버는 외부
공급자에 의존하므로 이 스모크 테스트가 특히 중요하다.**

**4. `collection/` — 엔진을 목으로 교체한 통합 테스트**

팬아웃, 재시도, 부분 실패 경로, 동시성 제한을 검증한다. 플랜별 팬아웃 수
(Starter 100 / Business 300)와 질의 팩 적용도 여기서 검증한다.

**5. E2E — 최소한만**

무료 진단 플로우 1개, 결제 플로우 1개. 그 이상은 유지보수 비용이 이득을 넘는다.

### 관측 — 원가를 실제로 봐야 한다

이 설계 과정에서 원가 계산이 두 번 틀렸다. 계산은 틀리고 실측만 맞는다.

`collection_runs`에 실행별로 기록한다.

- 엔진별 호출 수 · 토큰 사용량 · 추정 비용
- 소요 시간, 실패율
- 판정 1차 통과율 (원가를 좌우한다)

관리자 화면에 고객별 실제 원가율을 띄운다. 예상 12%가 실제로 12%인지 30%인지
첫 달에 알 수 있어야 한다. 모르고 6개월 운영하면 적자를 쌓는다.

SerpApi는 선약정이므로 **잔여 건수도 함께 추적한다.** 고객이 늘 때 어느 시점에
플랜을 올려야 하는지 미리 알아야 한다.

## 구현 전 확인할 항목

설계와 무관하게, 착수 전 사실 확인이 필요한 것들이다.

- **Trigger.dev 무료 크레딧($5)의 소진 속도.** 실행 시간에 비례해 소모되므로
  무료 진단 트래픽이 늘면 여기가 SerpApi보다 먼저 막힐 수 있다. 실제로 돌려봐야
  알 수 있고, 막히면 Hobby $10로 올리면 된다. **1단계 비용 추정의 유일한
  미확정 변수다.**
- **토스페이먼츠 수수료율.** 사업자 구분에 따라 달라 3%로 잡았다. 계약 시 확인.
- ~~**OpenAI 웹검색 툴의 호출당 단가.**~~ **확인 완료(2026-07-29): $10/1,000회,
  토큰과 별도 청구.** Gemini 3 grounding은 월 5,000건 무료 후 $14/1,000회.
  빠져 있던 이 요금 때문에 무료 진단 원가가 2~4배 과소 산정돼 있었고, 손익분기도
  Starter 2명 → 3명으로 밀렸다. "비용 구조" 절에 반영됨.
  **남은 미확정은 검색으로 딸려오는 본문 토큰 수**이며, 2단계 스모크 테스트에서
  실측한다. 이것이 현재 원가 추정의 가장 큰 불확실성이다.
- **도메인 확보 가능 여부.** `cited` 계열 도메인이 비어 있는지 확인하지 않았다.
- **SerpApi 네이버 AI 브리핑의 실제 커버리지.** 질의에 따라 AI 브리핑이 아예
  노출되지 않는 경우가 있다. 브리핑 미노출을 "언급 안 됨"으로 볼지 "측정 불가"로
  볼지 실제 응답을 보고 정해야 한다. 지표 정의에 영향을 준다.
