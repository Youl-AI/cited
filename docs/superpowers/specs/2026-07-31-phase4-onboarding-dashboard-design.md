# 4단계 설계 — 결제 없이 가는 온보딩·대시보드·정기 측정

2026-07-31 승인. 크몽 수익화 단계(같은 날 병합) 다음 단계다. 구
`2026-07-28-cited-phase-4-billing-and-onboarding.md`의 잔여 범위 중
**결제(Toss)를 뺀 전부**를 구현한다 — 플랜은 운영자가 수동 부여한다
(결제 도입 기준은 유지: 유료 고객 5명 또는 수동 청구 월 1시간 초과).

## 목표

**"운영자가 고객을 등록하면, 사이트가 매주 알아서 재고, 고객이 로그인해서
보는" 루프**를 완성한다. 크몽 DELUXE 고객에게 "계속 보고 싶으면 구독"을
팔 수 있는 상태가 된다 (수동 청구 — 계좌이체).

조각 다섯: ① 플랜 수동 부여 CLI ② 온보딩(브랜드 + 질의 에디터)
③ 정기 측정(GitHub Actions 스케줄 → API) ④ 풀 대시보드 ⑤ 실패 알림.

## 비용 전제 (사용자 확인됨)

- 개발 중 일회성: 에디터 생성 테스트 ~100원 + 파이프라인 검증 실측 ~2,400~4,800원
- 신규 구독료 0원 (GitHub Actions 방식)
- 운영 변동비: Starter 1명 = 질의 10 × 주 3회 ≈ **월 ~10,000원** (2엔진 실측
  단가). 결제가 없으므로 부여한 만큼 운영자 부담 — 돈 받는 고객만 부여하는
  것이 비용 통제 장치다.

## ① 플랜 부여 CLI

```
pnpm plan:grant <이메일> starter|business [--from-audit aud_xxx] [--packs N]
pnpm plan:revoke <이메일>
```

- `subscriptions` 행 생성/갱신 (기존 테이블 — plan·status·queryPacks).
- `--from-audit`: 크몽 진단 행을 온보딩 프리필로 연결. **크몽 건은 운영자
  이메일로 등록돼 있어 자동 매칭이 불가능** — 명시 연결이 유일한 길이다.
  연결 정보는 유저 행 또는 별도 열에 저장(구현 계획에서 확정).
- 웹 무료 진단 고객은 가입 이메일 = 인증된 신청 이메일로 자동 매칭해 프리필.
- 부여 전 가입 여부 확인 — 미가입 이메일이면 "먼저 가입을 안내하세요" 거부.

## ② 온보딩

가입 후 브랜드가 없으면 대시보드 대신 온보딩으로 보낸다.

**1단계 — 브랜드 정보**: 브랜드명·업종(25종 자동완성)·경쟁사(최대 플랜
한도)·도메인. **지역형 업종이면 지역 입력 필드 노출** — 무료 진단 웹 폼의
"지역은 CLI만" 결정은 그 폼의 것이고, 셀프서비스 온보딩은 지역 없이는
성립하지 않는다. 프리필: `--from-audit` 연결 행 또는 이메일 매칭 무료 진단.

**2단계 — 질의 에디터** (이 단계의 본체):
- 프리필: 크몽 전환이면 동결 질의 10개 그대로 (연속성 — 크몽 리포트와
  비교 가능). 아니면 업종 템플릿 3개 + [AI 후보 생성]으로 나머지 채움.
- 편집: 질의 수정·삭제·개별 재생성. 질의 수 = 플랜 한도(계정 전체 —
  Business는 브랜드에 나눠 쓴다).
- 실시간 검증: `validateCustomQueries` 재사용 — 브랜드명·경쟁사명 포함
  거부, 중복, 개수, 템플릿 3개 포함. 화면이 이유를 그 자리에서 보여준다.
- **생성 한도: 브랜드당 누적 5회** (LLM 비용 남용 방지, 초과 시 "직접
  수정해 주세요"). 생성 프롬프트에 브랜드명 미포함(기존 생성기 재사용).
- [확정] = 동결. 동결 후 수정은 운영자 CLI로만 (전후 비교 불변식).

**3단계 — 완료**: 다음 측정 시각 예고 ("월요일 새벽에 첫 측정이 돕니다").

## ③ 정기 측정

- **GitHub Actions cron** (월·수·금 KST 새벽 창, 15분 간격 반복)이
  `POST /api/cron/measure`를 호출. `CRON_SECRET` 헤더 인증.
- 핸들러는 **호출당 측정 대상 브랜드 1개** 처리 — 실측 1브랜드 233초로
  함수 한도(300초) 안. 브랜드가 여러 개면 다음 호출이 이어받는다 (큐 없는
  소진 방식). due 판정과 중복 실행 잠금은 collection_runs 상태로.
- 측정 = 기존 수집·판정 파이프라인 + 계정 전체 한도 검증(`validateRunStart`)
  그대로. 동결 질의 사용.
- 실패: 운영자 메일 + 다음 호출에서 재시도 1회. 재실패면 해당 회차 건너뜀
  (다음 스케줄에 정상 측정 — 공백 1회가 잘못된 데이터보다 낫다).

## ④ 저장

- `collection_runs`에 `result` jsonb 열 추가 (additive 마이그레이션) —
  회차마다 `AuditResult` 형태 스냅샷 저장(기존 buildAuditResult 재사용).
- 추이·히트맵·점유율은 스냅샷들에서 계산. 회차 상세는 기존 `ResultView`
  재사용 — 진단 리포트와 같은 화면 문법.

## ⑤ 풀 대시보드

- 브랜드 선택(복수 브랜드), 최신 언급률+구간 헤드라인.
- **추이 차트**: 회차별 언급률 점 + 오차 밴드(Wilson 구간), 엔진별 토글.
  점만 찍고 구간을 감추지 않는다 — 화면 문법은 리포트와 동일.
- **질문별 히트맵**: 질의 × 회차 언급률 매트릭스 — "어느 질문에서 비는가"가
  가장 실행 가능한 정보다.
- 경쟁사 점유율 추이 · 출처 상위 변화(도메인별 인용 수) · 회차 목록 → 상세.
- 디자인: 계측 미학 유지 ("sans는 말, mono는 계측값"), dataviz 규칙 적용.
  신규 화면이므로 디자인 패스를 PDF 때처럼 제대로 태운다.

## 보안·품질

- cron 엔드포인트 `CRON_SECRET` (타이밍 세이프 비교), 그 외 인증 없음 경로
  추가 금지.
- 에디터·대시보드는 본인 소유 브랜드만 (세션 검증).
- 생성 한도 서버 강제 (클라이언트 카운터 신뢰 금지).
- 테스트: 온보딩 E2E 완주(질의 확정까지, LLM은 인터셉트) · cron 핸들러 DI
  단위 테스트(브랜드 선택·잠금·재시도) · 에디터 검증 로직 단위 테스트 ·
  대시보드는 스냅샷 픽스처 렌더 테스트. 측정 실측 검증 1회는 수동.

## 성공 기준

- plan:grant → 온보딩 완주 → GitHub Actions 실측 1회 → 대시보드에 점 1개
  찍히는 전 루프가 실계정으로 1회 완주된다
- 크몽 전환 시나리오: --from-audit 연결 → 질의 10개 프리필 확인
- 측정 실패 시 운영자 메일 수신 확인
- `pnpm test`·`typecheck`·`lint`·`build`·`test:e2e` 전부 통과
