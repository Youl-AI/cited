### 이 실측이 잡은 버그

**리포트 메일이 `http://localhost:3000/audit/…` 링크를 달고 나갔다.** 운영자
CLI는 `.env.local`을 읽으므로 `NEXT_PUBLIC_APP_URL`이 개발용 값이다. 같은
변수가 웹 라우트에서는 옳고 CLI에서는 틀리다. 실측을 안 했으면 **첫 고객
리포트에서 터졌을 것이다.** 고침: `5c2b545` (`--base-url` + 로컬 주소 거부 +
`audit:resend`).

## 운영자 시간 — 자동화를 미루는 근거

**1건당 사람 손은 1~2분이다.** 명령 두 개가 전부다:

```bash
pnpm audit:list                                      # 대기 목록
pnpm audit:run <id> --base-url https://cited.co.kr   # 실행 후 발송
```

기계 시간 97초는 그냥 기다리는 시간이라 그동안 다른 일을 할 수 있다. 실제로
붙잡히는 것은 알림 메일을 보고 명령을 붙여넣는 정도다.

그래서 **4단계에서 Trigger.dev 자동화를 서두를 이유가 없다.** 하루 10건이
들어와도 하루 20분이다. 결제를 먼저 붙이는 것이 맞다. 자동화를 다시 검토할
기준은 "하루 30건" 또는 "리포트 발송까지 24시간을 넘기기 시작할 때"다.

## 확인이 끝난 것

- **리포트 화면의 `noindex`** — 발송된 리포트에서 확인.
  `<meta name="robots" content="noindex, nofollow">`
  (E2E로는 볼 수 없다. `notFound()`가 발동하면 Next.js가 라우트의 `metadata`를
  적용하지 않아, 존재하지 않는 ID로는 그 태그가 나오지 않는다.)
- **리포트 메일 수신** — Gmail 받은편지함 도착, 스팸함 아님. 링크도 열린다.
- **확인 메일 수신** — 신청 플로우에서 도착 확인.

## 아직 확인하지 못한 것

- **`--dry` 없이 바로 발송했다.** 이번에는 앞서 `--dry`로 결과를 본 뒤였지만,
  앞으로도 초기에는 `--dry`를 먼저 돌려 눈으로 보고 보내는 것이 맞다.
  자동 발송으로 넘어가는 기준은 "손으로 고칠 게 없어진 시점"이다.
- **외부 고객(우리 도메인이 아닌 수신자) 메일이 스팸함으로 가는지** — 확인한
  것은 운영자 본인 Gmail이다. 첫 외부 고객에서 다시 봐야 한다.

## E2E의 경계 — 왜 성공 경로를 가로채는가

`tests/e2e/free-audit.spec.ts`의 성공 경로는 `/api/audit/request`를
`page.route`로 가로챈다. 실제로 밟으면 **진짜 DB에 행이 생기고 Resend가 진짜
메일을 보낸다.** 계획서 원안의 수신자는 `e2e-…@cited-smoke.invalid`였는데,
`.invalid`는 존재할 수 없는 TLD라 두 결과 중 하나가 된다:

- Resend가 거부 → 라우트가 502 → 테스트가 원인과 무관하게 항상 실패
- Resend가 수락 → 하드 바운스 누적 → **발송 도메인 평판이 깎인다**

확인 메일이 스팸함으로 가기 시작하면 이 제품은 죽는다. 그래서 후자가 더 나쁘고,
성공 경로는 네트워크 경계에서 끊는다. 서버 쪽 동작은 `handlers.test.ts`가
의존성 주입으로 DB도 메일 서버도 없이 검증한다. **진짜 끝단 확인은 위의 수동
1건이 맡는다** — 자동화된 E2E가 그 자리를 대신하는 척하면 안 된다.
