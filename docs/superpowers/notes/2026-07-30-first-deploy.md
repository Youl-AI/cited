## 아직 측정하지 못한 것

**진단 1건을 프로덕션에서 끝까지 돌리는 것은 아직 하지 않았다.** 이것이
자동화 시점을 결정할 숫자를 만드는 유일한 방법이므로 미룰 수 없다:

- **운영자 시간** — 알림 메일을 본 순간부터 리포트 발송까지. 이 값이 4단계에서
  Trigger.dev로 자동화할지, 손으로 몇 건 더 버틸지를 가른다.
- **실제 원가 1건** — `audit:run`이 출력하는 `costMilliKrw`.
- **리포트 화면의 `noindex`** — E2E로는 볼 수 없다. `notFound()`가 발동하면
  Next.js가 라우트의 `metadata`를 적용하지 않아서, 존재하지 않는 ID로는 그
  태그가 나오지 않는다. **발송된 리포트가 하나 생긴 뒤에** 페이지 소스에서
  확인해야 한다.
- **확인 메일·리포트 메일이 스팸함으로 가는지** — 위에서 확인한 것은 운영자
  알림 1통뿐이다. 외부 수신자(예: Gmail)로 가는 경로는 따로 봐야 한다.

절차:

```bash
# 1. https://cited.co.kr 에서 본인 주소로 신청
# 2. 확인 메일 링크 클릭 → state=verified 화면
# 3. contact@cited.co.kr 로 운영자 알림 도착 확인
pnpm audit:list                 # 대기 1건
pnpm audit:run <id> --dry       # 눈으로 확인 (질의에 브랜드명이 없는지, 별칭이 비지 않았는지)
pnpm audit:run <id>             # 발송
# 4. 리포트 메일 → /audit/<id> → 페이지 소스에서 noindex 확인
```

## E2E의 경계 — 왜 성공 경로를 가로채는가

`tests/e2e/free-audit.spec.ts`의 성공 경로는 `/api/audit/request`를
`page.route`로 가로챈다. 실제로 밟으면 **진짜 DB에 행이 생기고 Resend가 진짜
메일을 보낸다.** 계획서 원안의 수신자는 `e2e-…@cited-smoke.invalid`였는데,
`.invalid`는 존재할 수 없는 TLD라 두 결과 중 하나가 된다:

- Resend가 거부 → 라우트가 502 → 테스트가 원인과 무관하게 항상 실패
- Resend가 수락 → 하드 바운스 누적 → **발송 도메인 평판이 깎인다**

확인 메일이 스팸함으로 가기 시작하면 이 제품은 죽는다. 그래서 후자가 더 나쁘고,
성공 경로는 네트워크 경계에서 끊는다. 서버 쪽 동작은 `handlers.test.ts`가
의존성 주입으로 DB도 메일 서버도 없이 검증한다. **진짜 끝단 확인은 위의 수동
1건이 맡는다** — 자동화된 E2E가 그 자리를 대신하는 척하면 안 된다.
