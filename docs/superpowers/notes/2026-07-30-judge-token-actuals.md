# 2차 판정(claude-haiku-4-5) 토큰 실측

측정일: 2026-07-30 · 모델 `claude-haiku-4-5-20251001` · `output_config.format` 구조화 출력

## 측정값

3건을 한 배치로 묶어 판정:

| 항목 | 값 |
| --- | --- |
| 입력 토큰 | 920 |
| 출력 토큰 | 213 |
| 판정 건수 | 3 |

시스템 프롬프트가 입력의 대부분이다(약 300토큰). **배치가 커질수록 건당
입력 원가가 떨어진다** — 시스템 프롬프트를 한 번만 싣기 때문이다. `runStage2`의
기본 배치 크기 20이 여기서 나온다.

## 건당 원가

`JUDGE_PRICING` = in $1/MTok · out $5/MTok (`src/lib/engines/pricing.ts`), 환율 1,400원:

```
in : 920 / 1e6 × $1 = $0.00092
out: 213 / 1e6 × $5 = $0.001065
합 : $0.001985 ≈ 2.8원  (3건) → 건당 약 0.93원
```

수집 엔진 원가(Gemini 32.9원/호출)에 비하면 **무시할 수준**이다. 2차 판정을
아끼려고 1차 매칭을 느슨하게 만들 이유가 없다 — 재현율을 우선하라는 Task 7의
설계 판단이 원가 면에서도 옳다.

## 프롬프트가 측정값을 바꾼다

시스템 프롬프트 없이 "브랜드 판정기"라고만 주고 같은 입력을 넣으면:

- `position`이 **문자 오프셋**(18)으로 돌아온다. "몇 번째로 언급된 브랜드인가,
  1부터 센다"를 명시해야 2가 나온다.
- `context`가 답변 원문을 그대로 되돌려준다.

즉 `SYSTEM_PROMPT`는 설정이 아니라 **측정 기구의 일부**다. 바꾸면 지난
측정치와의 비교 가능성이 깨진다. 골드 라벨 회귀 테스트(Task 10)를 먼저
통과시켜라. 같은 함정을 Gemini `SYSTEM_PROMPT`에서 이미 한 번 겪었다
(`2026-07-29-gemini-token-actuals.md` 참고).
